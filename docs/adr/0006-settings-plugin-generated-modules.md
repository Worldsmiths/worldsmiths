# ADR-0006: Generated platform modules through a settings plugin

- Status: accepted
- Date: 2026-11-12
- Deciders: founder
- Related: Spike S1, FR-B01, FR-B04, FR-B05, FR-B12, HLD §5.1, [R01 §6.3], [R02 §5.3]

## Context

FR-B01 asks for platform targets to be real, generated subprojects of the user's build, with no hand-written platform code. FR-B04 asks for the user's full dependency graph to reach every platform module. The OIS prototype passed only the user's own jar, and it ran a nested Gradle build through the Tooling API. FR-B05 asks for configuration-cache compliance and no nested builds. Gradle 10 will enable the configuration cache by default.

Spike S1 asked whether a Gradle settings plugin can `include` a generated `:desktop` module, give it the full user classpath, and stay configuration-cache clean on the repo's wrapper (Gradle 9.9.1). The roadmap gate: if it fails, fall back to a template plus a project plugin.

## Options considered

1. **Settings plugin that generates and includes the platform modules.** The user writes no platform code, the IDE sees ordinary subprojects, and dependencies flow through normal project dependencies. Risk: settings-time file writes and configuration-cache invalidation.
2. **Template plus a project plugin** (the roadmap fallback). The template ships the `desktop/` module and the project plugin configures it. Simple and cache-friendly, but the user owns platform files from day one, and engine upgrades have to migrate them.
3. **Hidden nested build** (OIS). Rejected by FR-B05.

## Decision

Option 1. The spike works, with the caveats below.

`io.github.worldsmiths.settings` (`WorldsmithsSettingsPlugin`) adds a `worldsmiths { gameModule; gameClass }` extension. In `settingsEvaluated` it writes `.worldsmiths/gen/desktop/build.gradle.kts` (one tiny file, plus a self-ignoring `.worldsmiths/.gitignore`), includes `:desktop`, and points its `projectDir` at that directory. The generated script applies the project plugin `io.github.worldsmiths.desktop` (`DesktopPlugin`), which:

- adds `implementation(project(gameModule))`, so the game's `api` and `implementation` dependencies reach `:desktop`'s runtime classpath;
- generates the launcher source in a cacheable task (`wsGenerateLauncher`) that references the game class directly, with no reflection;
- applies `application`, so `:desktop:run` / `wsRunDesktop` run the launcher.

Evidence: `SettingsPluginFunctionalTest` (TestKit, Gradle 9.9.1, `--configuration-cache` on every run):

- `desktopRunsGameWithFullClasspathAndReusesConfigurationCache`: the first run prints `Configuration cache entry stored.`, the launcher prints the game's output (computed with commons-lang3), and `wsPrintRuntimeClasspath` lists `game.jar` and `commons-lang3-3.17.0.jar`, which the game declares as `implementation`. The second run prints `Reusing configuration cache.`
- `editingGameSourcesKeepsTheConfigurationCache`: an edit to a game source reuses the cache and runs the new code.
- `deletedGeneratedModuleIsRestoredOnCacheHit`: deleting `.worldsmiths/` still reuses the cache, and the file is written again.
- `unknownGameModuleFailsWithClearMessage`.

All four also passed once with `-Dorg.gradle.unsafe.isolated-projects=true` (manual run, not kept in the suite).

## Consequences

- **Settings-time writes go through a `ValueSource`.** The first version wrote files directly from plugin code. Gradle recorded "file absent" as a configuration input, so the second run printed `configuration cache cannot be reused because the file system entry '.worldsmiths/.gitignore' has been created`. `GeneratedModuleSource` fixes this: Gradle does not track its file access, re-runs it on every cache check and compares the returned content. This is a hard rule for every generated module: never touch the file system from settings or project plugin code outside a `ValueSource` or a task.
- **Settings-time output stays tiny.** Only the build script is written at settings time. Launcher sources, registries and manifests are generated by tasks with declared inputs and outputs.
- **Plugin ids.** A game applies `io.github.worldsmiths.engine` in `settings.gradle.kts`. That id is `WorldsmithsSettingsPlugin`. The empty project plugin that used to hold the id is gone, and the engine's own build does not apply it. Generated modules keep internal ids; desktop stays `io.github.worldsmiths.desktop`. The id remains in `gradle/libs.versions.toml`. Nothing was published, so the spike's `io.github.worldsmiths.settings` id is not kept.
- **Java level.** The generated `:desktop` compiles at `--release 8` (ADR-0004), and its launcher references the game class directly. When `:desktop` is configured, it reads the game module's Java release (or its target, when release is unset). Above 8, configuration fails with `worldsmiths.gameModule '<path>' compiles for Java N. Worldsmiths requires Java 8...`. A module that does not apply the Java plugin is not checked. A per-target override waits until a later probe shows a higher level running on every platform.
- **The DSL is evaluated in `settingsEvaluated`.** A wrong `gameModule` fails at configuration time with a clear message. Per-target DSL (`targets { desktop { … } }`, FR-B02) fits the same hook.
- **Not yet proven:** a real LWJGL3 window and natives (this spike's launcher only prints); Android (AGP inside a generated module), TeaVM and RoboVM in generated modules; the IntelliJ import of `.worldsmiths/gen/desktop`; and TestKit tests running offline (the test resolves commons-lang3 from Maven Central). Each of these needs its own TestKit test in M1/M2.
- **Eject (FR-B12)** becomes copying `.worldsmiths/gen/<target>` into the repo and removing it from the settings plugin's includes.
